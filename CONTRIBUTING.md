## Где проект сейчас

CRANE на стадии проектирования: в репозитории архитектура, оценка трудоёмкости и гайдбук, кода пока нет. Поэтому самый ценный вклад сейчас — критический взгляд на архитектуру. Правила для кода ниже начнут действовать с первого коммита кода; они опубликованы заранее, чтобы ожидания были понятны.

## Как помочь

| Что | Как |
| --- | --- |
| Нашли ошибку или слабое место в архитектуре | Issue с меткой `architecture`: раздел документации, что не так, к чему это приведёт, ваше предложение |
| Знаете, как сделать проще | Issue с меткой `proposal`: какую проблему решаете, альтернативы, чем жертвуем |
| Неточность, опечатка, устаревший факт | Pull request с правкой в `docs/product/`; для фактов приложите источник |
| Есть вопрос | Issue с меткой `question`. Вопрос, на который нет ответа в документации, — тоже сигнал, что документацию нужно улучшить |
| Опыт эксплуатации Nexus, Artifactory, реестров пакетов | Issue с меткой `field-experience`: реальные сценарии и боли ценнее предположений |

Перед новым issue поищите похожие. Одна тема — один issue.

```
docs/product/        архитектура решения — источник истины (20 разделов)

crates/ web/ cli/    код (появляется с первым кодом); раскладка — раздел 8
tools/

  bump-version.ts          бамп версий при выпуске
  build-guidebook.sh       сборка PDF генератором guidebook-render
  estimate-agent-hours.py  модель трудоёмкости из раздела 18
Taskfile.yml         единая точка входа: `task --list`

```

## Правила для документации

- **Язык.** Документация в `docs/product/` ведётся на русском. Корневые файлы (README, CONTRIBUTING, SECURITY, кодекс поведения) существуют на русском и в английском зеркале с суффиксом `-EN`; меняете один — обновите оба.
- **Стиль.** Короткие предложения, активный залог, термины из [глоссария](docs/product/99-glossary.md). Цифры подкрепляются расчётом или источником, оценки так и называются оценками. Без маркетинга и превосходных степеней.
- **Диаграммы.** Mermaid прямо в Markdown, с подписью `*Рис. N.M. …*` строкой ниже: так они видны в GitLab и GitHub и попадают в гайдбук.
- **Ссылки между разделами** — номером раздела («раздел 14.9»), не позицией на странице.
- **Гайдбук.** После правок соберите PDF: `tools/build-guidebook.sh`. Сборка идёт с `--strict`: если вы переписали фрагмент, к которому привязано оформление в `guidebook/manifest.yaml`, сборка остановится с предупреждением — обновите манифест.
- **Оценка трудоёмкости.** Добавили или убрали функциональность — обновите модули в `tools/estimate-agent-hours.py` и цифры в разделах 1 и 18.

## Правила для кода

Начнут действовать с первого кода.

- **Единая точка входа:** `task check` (подробнее в `AGENTS.md`). Хуки `lefthook` ставятся при `pnpm install`; не обходите их.
- **Архитектура кода:** Rust — DDD + hexagonal + clean architecture, web — Feature-Sliced Design ([раздел 8](docs/product/08-c4-l4-code.md), [раздел 15](docs/product/15-frontend.md)).
- **Секреты для compose и тестов PostgreSQL:** `cp .env.dist .env`, затем `task secrets:init` создаёт файлы секретов в `./secrets/` (каталог в `.gitignore`, существующие файлы не перезаписываются).
- **Правило четырёх:** не больше 4 файлов и 8 подпапок в папке, смешанные папки (файлы и подпапки) запрещены. Проверяет `task structure`.
- **TypeScript везде, где можно:** скрипты и конфиги на `.ts`; файлы `.mjs` в репозитории не принимаются.
- **Rust:** стабильный toolchain; `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test` проходят без замечаний. Стиль — «скучный Rust» из [раздела 3](docs/product/03-load-forecast-rust-vs-fastapi.md): без собственных процедурных макросов и сложной магии типов.
- **Зависимости:** только пермиссивные лицензии; `cargo deny check` (лицензии и advisories) обязателен. Новая зависимость объясняется в описании pull request.
- **Frontend:** TypeScript strict, линтер и тесты (Vitest, Testing Library, Playwright) проходят без замечаний.
- **Тесты.** Любое изменение поведения сопровождается тестом. Тесты строго по AAA (`// Arrange`, `// Act`, `// Assert`, в Act один оператор; несколько проверок в Assert допустимы, только если это грани одного исхода) и проверяют только логику, а не код: геттеры, `Debug`/`Display` и тесты, убивающие мутанта в коде без логики, не пишутся. Соответствие проверяет `task structure`; полные правила — в [AGENTS.md](AGENTS.md). Критический путь (протоколы форматов, доступ, CAS и публикация, токены) дополнительно проверяется мутационным тестированием (cargo-mutants, Stryker). Полный гейт `task gate` запускается локально перед PR в `release/*`.
- **Безопасность.** Никаких секретов в коде, тестовых данных и журналах; секреты оборачиваются в тип, который не печатается. Недоверенные данные (содержимое пакетов, metadata, ответы моделей) никогда не влияют на права.
- **Совместимость.** Изменения протоколов проверяются матрицей реальных клиентов; изменения схемы БД — по схеме expand / migrate / contract (раздел 16.4).

## Коммиты и подпись DCO

- Сообщения коммитов по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): `feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:`. Тема в повелительном наклонении, до 100 символов. Проверяет commitlint (хук `commit-msg` и CI).
- **Атрибуция ИИ-агентов запрещена**: никаких `Co-Authored-By: <агент>`, «Generated with …», 🤖 в коммитах и описаниях PR. Автор вклада — человек, который за него отвечает.
- Один коммит — одно логическое изменение.
- Каждый коммит подписывается по [Developer Certificate of Origin](https://developercertificate.org/): `git commit -s` добавляет строку `Signed-off-by: Имя <email>`. Подписью вы подтверждаете, что имеете право передать этот вклад под лицензией проекта. CLA подписывать не нужно.

## Pull request и ревью

1. Создайте ветку от `main`, держите pull request небольшим и сфокусированным. PR открывается в `release/vX.Y.Z` (не в `main`); в `main` идёт только сам релиз.
2. В описании: что изменено и зачем, ссылки на issue и разделы документации, как проверено.
3. Все проверки CI зелёные.
4. Нужно одобрение сопровождающего; для доступа, токенов, криптографии, протоколов и аудита — двух, один из которых отвечает за безопасность.
5. Замечания ревью обсуждаются в pull request; решение фиксируется там же.
6. Слияние в `release/*` через squash; заголовок PR — по Conventional Commits, в описании таблица ручных мутантов; полный `task gate` — перед PR релиза в `main`.
7. После одобрения релиза PR `release/vX.Y.Z` → `main` сливается merge commit; версии, CHANGELOG и тег `vX.Y.Z` выставляет workflow `release` ([раздел 16.7](docs/product/16-deployment.md)).
