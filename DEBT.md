# Технический долг

Закрываем после того, как репозиторий станет публичным (минимум — полное ядро по плану, веха v0.5.0 в [ROADMAP.md](ROADMAP.md)).

| # | Долг | Условие | Что сделать |
| --- | --- | --- | --- |
| 1 | Защита веток `main` и `release/**` | Репозиторий публичный | Rulesets: PR обязателен, `main` — только merge commit, `release/**` — только squash, required checks (`branch-flow`, `title`, `structure`, `rust`, `web`, плюс `gate-mark` для `main`), запрет force-push и удаления; GitHub App `crane-release` в bypass для `main`. Файлы в `.github/rulesets/` и задача `task gh:rulesets`. |
| 2 | Автовыпуск версий | Включена защита веток | Создать GitHub App `crane-release`, положить `RELEASE_APP_ID` (variable) и `RELEASE_APP_PRIVATE_KEY` (secret); проверить `release` и `publish` на реальном релизе; опубликовать GitHub Release для `v0.0.0`. |
| 3 | Storybook и Playwright | Первый UI (v0.4.0) | Настроить, подключить `e2e` в `task gate` и Storybook lint/tests в CI на PR в `main`. |
| 4 | Сборка гайдбука | Появится `../guidebook-render` | Собрать PDF после правок разделов 2, 8, 13, 15–19. `guidebook/` вне git. |
| 5 | Sweeper staging-объектов на локальной ФС | Адаптер `BlobStore` на локальной ФС (v0.1.0) | В S3 брошенные `staging/<uuid>` убирает lifecycle по префиксу и возрасту; на файловой системе чистить некому. Добавить периодическую задачу: удалять `staging/*` старше 24 ч; покрыть тестом на возраст и на то, что закоммиченные blob не затрагиваются. |
| 6 | Статический токен | Модель доступа v0.4.0 | Заменить `CRANE_TOKEN`, `CRANE_TOKEN_FILE` и ключи `token`, `token_file` файла токенами `crp_`/`crr_`/`crci_` и политиками Cedar, убрать обе переменные. |
| 7 | Владельцы cargo | Команды workspace v0.4.0 | `GET .../owners` отдаёт единственную личность `crane`, `PUT` и `DELETE` дают 501; владельцы станут командами workspace. |
| 8 | Проверки публикации cargo | Раздел 13 реализован | Публикация не сверяет `Cargo.toml` внутри `.crate` с метаданными и не защищает пространства имён. |
| 9 | Тело публикации в памяти | Потоковая загрузка | Тело `PUT /api/v1/crates/new` буферизуется целиком до `CRANE_MAX_PUBLISH_BYTES`; разбирать кадры потоком. |
| 10 | `cargo search` | Нужен поиск по реестру | `GET /api/v1/crates?q=` не реализован. |
| 11 | Аудит входа: 3002 Success | Вход по ID token (v0.4.0) | Успешная аутентификация не аудируется (решение владельца): статический токен проверяется на каждом GET индекса, а в v0.4.0 каждая запись цепочки хэшей сериализуется. Успех виден как `actor` в `crane::access` и в каждом событии 6003. |
| 12 | Отказы до use case | Журнал аудита v0.4.0 | Отказы до вызова use case (битый кадр публикации, смена написания имени, превышение предела тела) видны только в access-журнале (`crane::access`), событий аудита у них нет. |
| 13 | `request_id` в cargo-ошибке | Нужен машинный разбор ошибок cargo | В теле ошибки cargo идентификатор запроса стоит только суффиксом `detail` (`(request_id …)`) и заголовком `X-Request-Id`: cargo показывает пользователю один `detail`. Отдельного поля нет. |
| 14 | Тексты лицензий и NOTICE сторонних зависимостей | Поставка в v0.5.0 | Бинарник и образ обязаны нести тексты лицензий и уведомления зависимостей (Apache-2.0, BSD-3-Clause, ISC, MIT, CDLA-Permissive-2.0 у aws-lc-sys, rustls, корней webpki и др.). Генерировать файл third-party notices (например, cargo-about) при сборке образа и класть в образ. |
