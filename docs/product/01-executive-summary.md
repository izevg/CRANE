# 1. Резюме для ЛПР

CRANE заменяет Nexus единым реестром для пяти экосистем и добавляет то, чего Nexus не даёт: прослеживаемость каждого пакета от коммита до потребителя, краткоживущие credentials для CI вместо долгоживущих секретов, объяснимые отказы доступа и единую картину CVE и лицензий.

- **1** бинарник и один образ на все профили: от ноутбука соло-разработчика до кластера корпорации
- **~50k** RPS пиковой нагрузки в профиле «корпорация», под которую проектируется горизонтальное масштабирование
- **~7 недель** до полного объёма P0–P3; промышленный релиз (P0+P1) через ~5 недель; ~808 агент-часов (из них ~55 — нагрузка и пентест после v1) и ~147 часов оператора (раздел 18)

## Ключевые решения

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Backend | **Rust** (tokio + axum), модульный монолит, один бинарник с ролями `serve` / `worker` / `all` | В 4–6 раз меньше CPU и RAM на пике, стабильный p99, минимальный профиль влезает в 1 vCPU / 1 ГБ (раздел 3) |
| Frontend | React + TypeScript на базе UI kit на Base UI, встраивается в бинарник | Единый стиль, готовые компоненты таблиц, диффов, метрик |
| Метаданные | PostgreSQL 17+ (единственный источник истины) | Транзакции для атомарной публикации, FTS и pgvector без отдельного поискового кластера |
| Кэш, лимиты, координация | Valkey (BSD-3) | Открытая лицензия BSD-3, совместим с протоколом Redis; кэш не является источником истины, его потеря не ломает данные |
| Файлы пакетов | Любое S3-совместимое хранилище через абстракцию; в комплекте SeaweedFS или RustFS (Apache-2.0); локальная ФС для соло-профиля | **MinIO под AGPL-3.0 и архивирован в феврале 2026**, поэтому не входит в поставку (раздел 17) |
| Расширяемость | Без системы плагинов. Форматы, интеграции и хранилища встроены как реализации внутренних трейтов (портов) | Меньше поверхность атаки и поддержки; новый формат = новый модуль за чётким интерфейсом |
| Развёртывание | Docker Compose single node и Helm chart для Kubernetes из одного образа | Оба сценария поддерживаются одинаково, отличается только топология |
| Уязвимости и SIEM | Открытые фиды (OSV, GHSA, NVD, KEV, EPSS), приоритет P0–P4, VEX, экстренная блокировка; события OCSF в SIEM, ответные действия SOAR | Поток CVE растёт быстрее, чем его можно разбирать вручную (раздел 14) |
| AI | Две функции: оценки риска моделями systemone (уязвимость, бласт, вирусность лицензии) и тексты LLM (объяснения, A2A-агент) | Числа нужны политикам, объяснения нужны людям (раздел 13) |
| Доступ и аудит | Keycloak (OIDC) для людей, краткоживущие токены CRANE для пакетных менеджеров и CI без хранимых секретов; роли с разделением обязанностей; журнал действий доступен только SecOps и аудитору | Меры приказа ФСТЭК № 21 по 152-ФЗ: разграничение доступа и регистрация событий (раздел 14.13) |
| Лицензия продукта | Apache-2.0 | Явный патентный грант, совместима со всем стеком |

## Что получает бизнес

- **Снижение рисков.** Защита от dependency confusion (внутренние имена никогда не уходят в публичный upstream), запрет перезаписи релизов, отсутствие долгоживущих токенов в CI, аудит с защитой от изменения.
- **Скорость команд.** Поиск по задаче, а не по имени; карточка пакета с командой установки; причина любого отказа с правилом и шагами исправления вместо «403».
- **Поток уязвимостей под контролем.** CVE выходят ежедневно, и ИИ ускоряет их появление. CRANE за 15 минут сопоставляет новое advisory с инвентарём, назначает приоритет P0–P4 с объяснением, создаёт задачи владельцам и при необходимости блокирует скачивание. Видно, какие пакеты, приложения, сборки и команды затронуты, с уровнем достоверности.
- **Прозрачность для ИБ.** Все события безопасности уходят в SIEM по открытой схеме OCSF с защитой от изменения; SOAR может блокировать версии и отзывать токены через API.
- **Стоимость владения.** Только OSS с пермиссивными лицензиями, без лицензионных платежей; минимальный профиль работает на одной небольшой ВМ.

## Что нужно решить до старта

1.  Подтвердить профиль нагрузки (раздел 3) и целевые SLO/RPO/RTO (раздел 4). От них зависит размер команды SRE и железо, но не архитектура.
2.  Утвердить лицензионную политику организации (категории и контексты использования, раздел 10.8).
3.  Согласовать требование «99.9999999%»: в документе показано, что девять девяток достижимы для **сохранности** данных, а для **доступности** реалистичный целевой уровень 99.95–99.99% (раздел 4).
4.  Зафиксировать контракт моделей systemone и LLM, набор write-навыков A2A-агента и схему событий SIEM (раздел 19, решения 10–11).
