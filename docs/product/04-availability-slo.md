# 4. Доступность, SLO, RPO/RTO

## О требовании 99.9999999%

> **Честная оценка.** 99.9999999% доступности означают ~32 миллисекунды простоя в год. Этого не обещают ни облачные провайдеры (типичный SLA 99.9–99.99%), ни исходные требования (active-active HA и геореплика вне первой версии). Девять и более девяток реальны для **сохранности (durability)** данных: S3-хранилища с erasure coding дают 11 девяток, а CAS с проверкой SHA-256 исключает тихую порчу.

Архитектура разделяет два класса операций, у которых разная достижимая доступность:

-   **Чтение (скачивание пакетов)** критично для сборок. Обслуживается stateless-репликами из кэша и S3; каждый запрос сверяется с каталогом (резервации и namespaces hosted, экстренные блокировки, quarantine), поэтому чтение переживает отказ primary только пока доступна read-реплика каталога. Если каталога нет совсем, чтение получает `503` (fail closed, «Режимы деградации»). Здесь цель 99.99% в профиле L достижима в одном регионе с тремя зонами.
-   **Запись (публикация, управление)** требует primary БД. При failover 10–30 секунд клиенты получают `503` с `Retry-After: 10`; стандартные клиенты и CI templates повторяют запрос.

## Профили SLO

Цели остаются целями: под реальной нагрузкой они подтверждаются после v1 (ROADMAP, «После v1»), регрессия задержек отслеживается с v0.5.0.

| Показатель | S | M | L |
| --- | --- | --- | --- |
| Доступность скачивания | 99.5% (одна ВМ) | 99.9% | 99.99% (3 зоны) |
| Доступность публикации | 99.5% | 99.9% | 99.95% |
| p99 metadata, кэш-хит (на сервере) | < 20 мс | < 10 мс | < 10 мс |
| p99 time-to-first-byte blob из кэша | < 50 мс | < 30 мс | < 30 мс |
| RPO metadata | ≤ 24 ч (снапшот) или ≤ 5 мин (WAL) | ≤ 1 мин (WAL-архив) | 0 (синхронная реплика) |
| RTO | ≤ 4 ч | ≤ 1 ч | ≤ 1 мин (failover), ≤ 4 ч (DR) |
| Сохранность blobs | зависит от диска | ≥ 99.999999999% (S3 EC) | ≥ 99.999999999% (S3 EC) |
| Время обнаружения уязвимости (advisory в фиде → finding) | ≤ 60 мин | ≤ 15 мин | ≤ 15 мин |
| Отставание экспорта в SIEM | ≤ 15 мин | ≤ 5 мин | ≤ 5 мин |
| Время применения отзыва credentials | ≤ 5 с типично (событие инвалидации), ≤ 30 с гарантированно (TTL кэша) |

## Режимы деградации

| Отказ | Поведение |
| --- | --- |
| Primary PostgreSQL | Пока доступна read-реплика, скачивания идут с неё; публикация и управление отвечают `503 Retry-After`; UI показывает баннер read-only. Если недоступен весь каталог (соединение, таймаут пула, остановка сервера), **все** протокольные запросы, включая proxy-чтения и попадания в кэш, получают `503 Retry-After`, выборок из upstream нет (fail closed): без каталога нельзя проверить резервации и namespaces (hosted важнее proxy), экстренные блокировки и quarantine, а отдать имя из upstream или кэша значит открыть typosquatting и dependency confusion. Безопасность важнее доступности (решение 46 раздела 19; тот же принцип в инварианте имён 14, решение 28). Баг (нарушенный инвариант) остаётся `500`, повторять его бессмысленно. |
| Valkey | Переход на кэш в процессе и локальные лимиты; рост нагрузки на БД ограничен circuit breaker'ом; данных не теряется. |
| Upstream (npmjs, PyPI, Maven Central, nuget.org, crates.io) | stale-if-error: отдаём закэшированные metadata до настраиваемого срока (по умолчанию 7 дней) с заголовком `Warning` (при 429/403 upstream не дольше 24 ч, при 410/451 не отдаём вовсе); отчёт «готовность сборки к офлайну». |
| Тихий обрыв соединения к upstream (NAT, файрвол) | CRANE шлёт HTTP/2 PING каждые 15 с, в том числе на простаивающем соединении; без ответа за 10 с соединение закрывается, и следующий запрос открывает новое, то есть мёртвое соединение замечается за ≈ 25 с, а не держит запросы до таймаута чтения. Соединение, простоявшее в пуле дольше 30 с, не переиспользуется (для HTTP/1.1, где PING нет). Без этого после паузы в трафике proxy отдавал бы 502 до перезапуска. |
| Trivy | Проверки помечаются «ошибка анализа» или «проверка отсутствует»; поведение promotion определяет политика, по умолчанию promotion блокируется, скачивание нет. Сопоставление advisory из фидов продолжает работать. |
| Фид уязвимостей | Используется последнее загруженное состояние; событие `feed.lagging` в SIEM и алерт; остальные фиды продолжают работать. |
| systemone (скоринг) | Приоритет и лицензионные решения считаются по правилам (CVSS, EPSS, KEV, категория SPDX); P0 по KEV и вредоносным пакетам не зависит от модели. |
| LLM | Нет объяснений и ассистентов; поиск лексический; A2A-агент отвечает структурированными данными. |
| SIEM | События копятся в outbox, экспорт продолжается с курсора после восстановления; аудит не теряется. |
| S3 | Скачивание тех объектов, что есть в кэше процесса или CDN, продолжается; остальное `503 Retry-After`. Публикация недоступна. Отказ S3 приходит клиенту за ~5 с (3 повтора, бюджет как у ожидания соединения с БД), а не за минуты. |
